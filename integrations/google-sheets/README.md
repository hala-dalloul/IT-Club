# ربط النموذجين بـ Google Sheets

هذا الملف هو جهة استقبال البيانات، وليس تفعيلًا للربط في الموقع. الكود الحالي للموقع لا يزال يستخدم Supabase للنموذجين، إلى أن يُنشر السكربت ثم يُربط رابط /exec وتُستبدل آلية الإرسال والعداد والتحكم في لوحة الإدارة.

1. افتحي أحد الشيتين، ثم Extensions > Apps Script، والصقي كامل Code.gs مكان الكود الافتراضي. استخدمي مشروع Apps Script واحدًا فقط للشيتين، حتى تشترك كل الطلبات في القفل نفسه.
2. من Project Settings > Script Properties أضيفي SUPABASE_PUBLISHABLE_KEY بقيمة المفتاح العام لمشروع Supabase. لا تضيفي service_role أو كلمة مرور. هذا المفتاح يُستخدم للتحقق من حساب المدير فقط؛ السكربت لا يكتب أي طلبات في Supabase.
3. شغّلي setup مرة واحدة من محرر السكربت ووافقي على الوصول للشيتين بحساب يملك صلاحية تعديلهما. يضيف تبويب رسائل الموقع في شيت التواصل وتبويب طلبات الموقع في شيت الانضمام، دون تعديل التبويبات الأخرى.
4. اختاري Deploy > New deployment > Web app، ثم Execute as: Me وWho has access: Anyone. إعداد Anyone يسمح باستقبال الطلبات العامة، ولا يوفّر قراءة بيانات الطلبات. لا توجد واجهة عامة لقراءة تلك البيانات.
5. انسخي رابط Web app الذي ينتهي بـ /exec وأرسليه لإكمال الربط في الموقع. لا ترسلي كلمة مرور أو رمز جلسة حسابك.

التسجيل يبدأ مغلقًا، والحد المبدئي 40. بعد ربط الإدارة، يمكن للمدير العام ضبط الحد وفتح أو إغلاق الاستقبال. العداد يحسب الصفوف المسجلة في تبويب طلبات الموقع؛ إعادة الفتح لا تصفّر العدد. لزيادة الاستقبال ارفعي الحد فوق العدد الحالي. لا تحذفي أو تعدلي معرفات الطلبات والرقم الجامعي؛ فهي تمنع التكرار. الطلبات القديمة في Supabase لا تنتقل تلقائيًا ولا تُحذف بهذا السكربت.

يُحفظ الرقم الجامعي كنص من 9 أرقام مع الحفاظ على الصفر الأول. يمنع تكرار الرقم الجامعي، وتُكتب الرسائل كنصوص حرفية لمنع تفسيرها كصيغ. العدّ والتحقق والكتابة ضمن قفل واحد لمنع تجاوز الحد بالطلبات المتزامنة. الأسماء والبريد والرسائل تُكتب في الشيت المحدد فقط.

## عقد الربط للموقع

- GET /exec يعيد {ok:true, registration:{open,enabled,limit,count,remaining}}.
- POST /exec، Content-Type: text/plain، والجسم JSON:
  - {action:"contact",requestId:"UUID",data:{name,email,message}}
  - {action:"join",requestId:"UUID",data:{fullName,email,phone,studentId,major,preferredCommittee,message}}
  - {action:"configure",accessToken:"جلسة المدير من Supabase",enabled:true,limit:40}
- احتفظي بنفس requestId عند إعادة محاولة نفس الإرسال. لا تعيدي استخدامه لطلب آخر.
- فشل الإرسال يُرجع ok:false وcode. يجب فحص JSON حتى لو كانت استجابة HTTP ناجحة.
- JOIN_CLOSED يعرض: تم وقف استقبال الأعضاء الجدد.
- ALREADY_REGISTERED يعرض: تم تسجيل طلب سابق بهذا الرقم الجامعي.
- BUSY يسمح بإعادة المحاولة بنفس requestId.
- لا تستخدمي fetch mode:no-cors: لا يمكن قراءة نتيجة الطلب ولن تعرفي هل حُفظ أم رُفض. يجب اختبار إعادة توجيه Google وCORS من عنوان الموقع الفعلي عند الربط؛ إذا منع المتصفح قراءة الرد يُستخدم وسيط خادم لا يحفظ بيانات الطلبات.
- إعدادات المدير تتحقق من صلاحية super_admin عبر Supabase لكل طلب؛ لا يكفي إخفاء الأزرار في الواجهة.

المصادر الرسمية: https://developers.google.com/apps-script/guides/web و https://developers.google.com/apps-script/reference/lock/lock-service
